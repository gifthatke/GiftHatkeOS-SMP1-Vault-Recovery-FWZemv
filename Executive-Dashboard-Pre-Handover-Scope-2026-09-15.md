# Executive Dashboard — Pre-Handover Implementation Scope

**Date:** 2026-09-15
**Status:** SCOPE DOCUMENT ONLY — NOT AN IMPLEMENTATION AUTHORIZATION
**Origin:** GAP-001's expanded-scope domain sweep (Domain 7), registered as PHB-6, consolidated plan Tier 1 item 4
**Governs:** pre-handover parity blocker for the Executive Dashboard first-screen content (Canon Domain 7, Reporting & Business Intelligence — specifically the Dashboards and KPI Governance capabilities)

This document is a precise implementation scope, built from a direct, complete read of the frozen source (`ExecutiveDashboardService.js`, `ExecutiveDashboardConfig.js`, `ExecutiveDashboardContracts.js`, `ExecutiveDashboardAdapters.js`, `ExecutiveDashboardNormalizers.js`, all read in full), the Canon Domain 7 Stage 10 certification text, and a direct, re-verified check of what already exists in Standalone. It is not a patch and contains no code. Writing or merging anything described here requires its own separate, explicit authorization and its own scope-lock/implementation/tests/regression/closure cycle. Standalone has not been handed over to employees; this is a pre-handover gap, not a live-incident fix.

## 0. What this scope targets, and what it deliberately does not

Canon Domain 7 certifies a large architecture: KPI Governance with a formal certification lifecycle (`Proposed → Defined → Validated → Certified → Published → Monitored`, §10.6), Dashboards, Reports, Scorecards, Forecasts, Analytical Datasets, Reporting Catalogs, and Alert Rules as permanently-owned named entities (§10.5, §10.7). **Frozen implements none of that governance ceremony.** What it actually built is narrower and pragmatic: a read-only aggregation layer that pulls whatever data each operational module's existing read API happens to expose, normalizes it against a completeness "contract," and renders it as one screen — no KPI proposal/validation/certification workflow, no persisted Scorecard or Forecast entities, no Reporting Catalog. Frozen's own header comment states this plainly: "ERP6 is a read-only aggregation layer. It must not duplicate or mutate business rules owned by ERP1–ERP5" (`ExecutiveDashboardConfig.js:5-6`) — a close practical echo of Canon §10.5's boundary text that Reporting "collaborates with — but does not own" Customer Orders, Inventory, Manufacturing, Shipping, or Financial Transactions. This scope document targets frozen's actual implemented structure, consistent with every other scope document in this series — not Canon's fuller KPI-governance/Scorecard/Forecast ceiling, which remains genuinely aspirational in both codebases.

## 1. Canon grounding

Canon Domain 7, §10.4 "Certified Business Capabilities" → "Dashboards," names three things: Executive dashboards, Department dashboards, Operational dashboards. Frozen implements exactly one of the three (Executive). §10.5's domain-boundary language (Reporting owns KPIs/Metrics/Dashboards/Alert Rules/Executive Intelligence but "collaborates with — but does not own" the operational domains it reports on) is the same non-ownership pattern already confirmed for Domain 11 in the Task/Work Board scope, and frozen's Dashboard honors it precisely: every write path stays in ERP1–ERP5; the Dashboard only ever reads.

## 2. What frozen actually implements — read in full, not excerpted

### 2.1 Workspace build, caching, and entry points

`executiveDashboardGetWorkspace(forceRefresh)` (`ExecutiveDashboardService.js:9-54`) checks a script-cache entry (120-second TTL, `ExecutiveDashboardConfig.js:12`) before rebuilding; on a cache miss it acquires a script lock, double-checks the cache (avoiding a duplicate rebuild under concurrent requests), then calls `executiveDashboardBuildWorkspace_()` and caches the result. `executiveDashboardInvalidateCache()` and `executiveDashboardGetDiagnostics()` (`:56-89`) are auxiliary entry points; the diagnostics one is not confirmed reachable from any UI (not checked further in this pass — low relevance to the actual employee-facing dashboard).

### 2.2 The "probing adapter" source-resolution pattern — and a significant finding about what's actually live

For each of five modules (`orders`, `production`, `inventory`, `shipping`, `finance`), `executiveDashboardReadSource_` (`ExecutiveDashboardAdapters.js:55-132`) tries a short, ordered list of **candidate global function names** and calls the first one that actually exists:

| Module | Candidates tried, in order |
|---|---|
| orders | `ordersGetExecutiveSummary`, `ordersGetDashboardSummary`, `orderGetDashboardSummary`, `ordersGetWorkspace` |
| production | `productionGetExecutiveSummary`, `productionGetDashboardSummary`, `productionGetPerformanceDiagnostics`, `productionGetWorkspace` |
| inventory | `inventoryGetExecutiveSummary`, `inventoryGetDashboardSummary`, `inventoryGetWorkspace` |
| shipping | `shippingGetExecutiveSummary`, `shippingGetDashboardSummary`, `shippingGetWorkspace` |
| finance | `financeGetExecutiveSummary`, `financeGetDashboardSummary`, `financeGetWorkspace` |

**Directly checked against the live frozen file list: none of the dedicated `*GetExecutiveSummary`/`*GetDashboardSummary` candidates exist anywhere in the repository, for any module.** The only candidate that resolves for orders, inventory, shipping, and finance is each module's plain, general-purpose `*GetWorkspace` function — the last item in each list. Production has one partial exception: `productionGetPerformanceDiagnostics` (`ProductionService.js`) does exist, so production gets a slightly richer source than the other four. Practically, this means frozen's own Dashboard is **not** backed by purpose-built executive-summary calculators for four of its five modules — it falls all the way back to fuzzy-matching whatever fields happen to already be present on each module's ordinary workspace response (`ExecutiveDashboardNormalizers.js`'s `executiveDashboardFirstValue_`/`FirstArray_` try several plausible field-name spellings per contract field, e.g. orders' `ordersToday` accepts `ordersToday`, `todayOrders`, or `newOrdersToday` — whichever the raw payload happens to have).

### 2.3 The completeness contract — exact required/optional fields per module

`ExecutiveDashboardContracts.js:9-114` defines, per module, a `required` and `optional` field list. A module is "Certified" only if every required field is present and non-null on its normalized payload; missing/invalid required fields drive both a per-module "Incomplete"/"Action required" status (`executiveDashboardBuildIntegrations_`, `ExecutiveDashboardService.js:297-318`) and a synthetic Critical alert (`executiveDashboardBuildAlerts_`, `:213-237`). Full field list, since this is the literal build target:

- **orders** — required: `ordersToday, ordersThisMonth, newOrders, pendingOrders, delayedOrders, cancelledOrders`. optional: `todaySales, monthlyRevenue, averageOrderValue, statusBreakdown, recentActivity, criticalAlerts, approvalRequests, salesTrend, topProducts, topCustomers, channelPerformance`.
- **production** — required: `jobsInQueue, jobsInProgress, completedToday, efficiency`. optional: `bottlenecks, workstationPerformance, recentActivity, criticalAlerts, approvalRequests, manufacturingPerformance`.
- **inventory** — required: `lowStockCount, outOfStockCount`. optional: `fastMovingProducts, deadStock, materialConsumption, recentActivity, criticalAlerts, approvalRequests`.
- **shipping** — required: `pendingShipments, readyToDispatch, deliveredToday`. optional: `courierPerformance, recentActivity, criticalAlerts, approvalRequests`.
- **finance** — required: `todaySales, monthlyRevenue, averageOrderValue, grossProfit, netProfit, cashPosition, receivables, payables, gstLiability`. optional: `cashFlowSummary, budgetVsActual, outstandingMarketplaceSettlements, recentActivity, criticalAlerts, approvalRequests, salesTrend`.

### 2.4 What the workspace actually renders (`executiveDashboardBuildWorkspace_`, `:91-132`)

- **Greeting** (`:163-178`) — pure time-of-day text, no data dependency.
- **7 executive KPI cards** (`:180-211`): Today's Sales, Monthly Revenue, Orders Today, Average Order Value, Gross Profit, Net Profit, Cash Position — sourced from the `finance`/`orders` normalized payloads (finance preferred where both could supply a value, via `executiveDashboardFirstNonNull_`).
- **Per-module raw data** (`orders`, `production`, `inventory`, `shipping`, `finance` — the full normalized payload, not just KPIs) is passed through on the workspace object directly (`:111-115`).
- **Alerts** (`:213-237`) — one synthetic "contract requires attention" alert per non-"ok" source, plus each source's own `criticalAlerts` array, sorted by severity, capped at 12 (`MAX_ALERTS`).
- **Approvals queue** (`:239-256`) — flattens every source's `approvalRequests` array, capped at 12.
- **Recent activity** (`:258-278`) — flattens every source's `recentActivity` array, sorted by timestamp descending, capped at 12 (`MAX_RECENT_ACTIVITY`).
- **Intelligence panel** (`:280-295`) — `salesTrend` (finance, falling back to orders), `topProducts`/`topCustomers`/`channelPerformance` (orders, capped at 8 rows), `manufacturingPerformance` (production, capped at 8 rows). **This overlaps directly with PHB-7** (per-module Executive/Business Intelligence) — see §5.
- **Integrations / system health** (`:297-340`) — per-module connection status (Certified/Incomplete/Action required) and an overall Healthy/Attention/Critical rollup based on how many of the five modules are fully certified.

### 2.5 Live UI wiring — confirmed

`Router.js:9-13`'s `APP.MODULES` includes `"Dashboard"`. `View_Dashboard.html` calls `executiveDashboardGetWorkspace` (confirmed in this audit's earlier expanded-scope pass). Unlike the Task/Work Board (PHB-5), Dashboard is not frozen's `DEFAULT_MODULE` — that is `"TodaysWork"` — but it is the next screen an employee reaches and is listed second in `APP.MODULES`, ahead of every operational module.

## 3. What already exists in Standalone

`apps/api/src/dashboard-service.ts` (read in full) composes exactly four things: `order.loadWorkspace()`, `production.loadWorkspace()`, `inventory.loadWorkspace()`, and a CRM follow-up work queue projected from `crm.getLeads()` (lines 97-149). No Finance, no Shipping, no KPI cards, no greeting, no alerts, no approvals queue beyond the CRM work-queue items, no recent-activity feed, no intelligence panel, no system-health/integration status. `apps/api/src/routes/dashboard.ts` exposes exactly one route, `GET /dashboard/workspace`, permission-gated on an existing `"Dashboard"` permission-catalogue key (already present — unlike Attachments/Notes/the Task Board, **no new permission key is needed for this item**).

Directly re-checked in this pass: none of §2.3's required contract-field names (`ordersToday`, `pendingOrders`, `jobsInQueue`, `lowStockCount`, `todaySales`, `grossProfit`, etc.) appear anywhere in `order-service.ts`, `production-service.ts`, or `inventory-service.ts` — these services return raw record collections, not pre-computed aggregates. `finance-service.ts` does hold `receivables`/`payables`, but as raw arrays of records (`readonly unknown[]`), not aggregate totals — so even Finance's overlap is partial, not a renaming exercise. **This is a build-from-scratch scope for the aggregation and computation layer**, though it can compose from workspace data that mostly already exists (unlike Attachments/Notes/the Task Board, which needed new persisted entities — the missing piece here is computation, not storage).

## 4. Proposed Standalone scope

Frozen's own required/optional split is a natural, already-battle-tested way to phase this:

**4.1 Phase A — required contract fields (drives the 7 KPI cards and the system-health/certification panel)**

For each of the five modules, someone implementing this needs to write actual counting/aggregation logic against Standalone's existing record stores — not just rename fields, since none of these values are currently computed anywhere:
- Orders: count of today's orders, this month's orders, new/pending/delayed/cancelled orders.
- Production: jobs in queue, jobs in progress, completed today, an efficiency figure (frozen's exact efficiency formula was not traced in this pass — would need to be read from `ProductionService.js` at implementation time if exact parity is wanted, or a reasonable Standalone-native definition chosen instead, which is a decision this document does not make).
- Inventory: low-stock count, out-of-stock count.
- Shipping: pending shipments, ready-to-dispatch count, delivered-today count.
- Finance: today's sales, monthly revenue, average order value, gross profit, net profit, cash position, receivables total, payables total, GST liability — several of these (receivables/payables totals specifically) are straightforward sums over data Finance already holds; others (gross/net profit, cash position) would need their calculation basis confirmed against frozen's Finance logic or Standalone's own existing `executiveFinanceIntelligence()` (already ported per PHB-7's scope, and likely able to supply some of these numbers directly rather than requiring a second calculation).

**4.2 Phase B — optional fields (alerts, approvals queue, recent activity, intelligence panel)**

- `recentActivity`/`criticalAlerts`/`approvalRequests` per module — Approvals could reasonably source from the existing `customer-approval-service.ts` for the Personalization-related approval type frozen itself surfaces here; the other module-specific alert/activity feeds are new small aggregations, lower stakes than Phase A since they don't affect certification status.
- `salesTrend`/`topProducts`/`topCustomers`/`channelPerformance`/`manufacturingPerformance` — **this is the same underlying capability as PHB-7** (per-module Executive/Business Intelligence), not a separate build. If PHB-7 is ever authorized and implemented, this piece of the Dashboard should consume its output rather than be built twice; if only PHB-6 is authorized, a minimal version of just these five fields (without PHB-7's fuller bottleneck/risk-scoring/forecast logic) would need to be built as a narrower stand-in. This document does not decide which order to build these in — see §5.

**4.3 The orchestration layer**

- **Application-service method**: extends (or sits alongside) `dashboard-service.ts`'s existing `loadWorkspace()` — a decision point, not prescribed here, since the existing method is already consumed by the current route and changing its shape has a blast radius of one (the single `/dashboard/workspace` route, confirmed by direct read), which is a small, contained change either way.
- **Design question, not a requirement**: frozen's own contract-validation/completeness-scoring/probing-adapter machinery (§2.2-§2.3) is a real, deliberate piece of engineering — it's what lets frozen degrade gracefully when a module's data isn't fully available rather than failing the whole dashboard. A Standalone implementation could reasonably choose to reproduce this ceremony (useful if Standalone's own modules might independently evolve and drift out of sync) or skip it in favor of directly computing the required fields against Standalone's own always-available services (simpler, since Standalone doesn't have frozen's dynamic-global-function-resolution problem — Standalone's services are statically wired, not probed at runtime). This document flags the choice; it does not make it.
- **Route**: `GET /dashboard/workspace` already exists and is already permission-gated — this item extends its response shape rather than requiring a new route or a new permission key.

## 5. Cross-cutting notes

**Overlap with PHB-7, not duplication.** §4.2's intelligence-panel fields and PHB-7's per-module Business Intelligence services describe the same underlying frozen capability, approached from two different entry points (the Dashboard's summary view vs. the deeper Reports workspace). Whoever sequences implementation should treat these as one body of work with two consumers, not two separate builds — building PHB-7's per-module Intelligence services first would let PHB-6's intelligence panel simply consume their output.

**Overlap with Finance's `executiveFinanceIntelligence()`.** Standalone has already fully ported frozen's Finance Intelligence logic (per this audit's expanded-scope sweep), reachable via `GET /reports/financial`. Several of Phase A's finance KPI fields (grossProfit, netProfit, possibly cashPosition) may already be computable by calling into that existing service rather than writing new Finance aggregation logic from scratch — worth checking at implementation time before duplicating work.

**Graceful degradation is a deliberate frozen design choice worth preserving**, independent of whether the contract-validation ceremony itself is carried over: each of frozen's five source reads is independently try/caught (implicit in `executiveDashboardReadSource_`'s per-candidate try/catch, `ExecutiveDashboardAdapters.js:80-114`), so one module's data being unavailable produces a partial dashboard with a warning, not a broken page. Standalone's own `dashboard-service.ts`/`reports-service.ts` currently compose sources with a single `Promise.all` (`dashboard-service.ts:103-121`) — meaning one source failing today would fail the whole workspace load. Flagged as worth a deliberate decision either way, not assumed.

## 6. Explicitly out of scope for this document

- Canon's fuller KPI-governance lifecycle (Proposed→Defined→Validated→Certified→Published→Monitored, §10.6) and persisted Scorecard/Forecast/Reporting-Catalog entities as named, governed things — none of this exists in frozen; building it would be new capability beyond parity, not a migration gap. See §0.
- Department and Operational dashboards (Canon §10.4 names three dashboard types; frozen implements only Executive) — not found in frozen, not proposed here.
- The deeper per-module Intelligence computation itself (trend/ranking/bottleneck/risk-scoring logic) — that is PHB-7's scope, cross-referenced in §5, not repeated here.
- `executiveDashboardGetDiagnostics()` / cache-invalidation endpoints (`ExecutiveDashboardService.js:56-89`) — auxiliary, not confirmed UI-reachable, low relevance to the employee-facing screen this document scopes.
- Frozen's exact contract-validation/probing-adapter mechanism as a hard requirement — flagged in §4.3 as a design choice, not decided.

## 7. Suggested sequencing, not an authorization

If authorized: (1) Phase A's required aggregation fields per module — this alone unlocks the 7 KPI cards, the highest-visibility piece of the missing screen; (2) the orchestration method (greeting + KPI assembly + a chosen degradation strategy); (3) Phase B's optional fields, coordinated with PHB-7 per §5 rather than built independently. Given PHB-7's Finance Intelligence piece is already complete, Finance-derived KPI fields in Phase A are a reasonable place to start implementation, if this is authorized before PHB-7's other five modules are.

## 8. Implementation record, 2026-09-15 — Phase A (required fields, KPI cards, system health)

Authorized and implemented in this session, following §7's sequencing, parts (1) and (2). **Nothing has been committed or pushed.** Phase B (§4.2 — alerts, approvals queue, recent activity, the intelligence panel) was **not** built in this increment, per §7's own recommendation to coordinate it with PHB-7 rather than build it independently — PHB-7 is not yet implemented, so a "minimal stand-in" version of Phase B was deliberately deferred rather than built now and likely rebuilt later.

**Design questions §4.3 explicitly left open, resolved here:**
- **Orchestration**: extended `dashboard-service.ts`'s existing `loadWorkspace()` with one new additive `executive` field, exactly as §4.3 suggested — blast radius stayed at the one existing `/dashboard/workspace` route; no new route or permission key was needed.
- **Contract-validation ceremony**: skipped, in favor of a simplified two-state per-module health signal (`"ok"`/`"unavailable"`, reflecting whether that module's own read actually succeeded) plus a three-tier overall rollup (Healthy/Attention/Critical). Frozen's fuller per-field Certified/Incomplete/Action-required completeness contract was not built — Standalone's services are statically wired, not runtime-probed the way frozen's global-function-resolution pattern requires, so there is no equivalent "is this source even reachable" question to certify against, only "did this read succeed."
- **Graceful degradation**: built as a genuine improvement over this codebase's own existing pattern — `dashboard-service.ts`'s pre-existing four sources are still composed with one `Promise.all` (unchanged, out of this increment's scope), but the new Executive Dashboard slice independently try/catches each of its five sources internally, matching frozen's own design exactly, so one module's data being unavailable degrades that module to zero-valued fields with a warning rather than breaking the whole KPI screen.

**Built:** Pure computation functions in `packages/domain/src/executive-dashboard.ts` — `buildExecutiveDashboardGreeting`, `computeExecutiveOrdersSummary`, `computeExecutiveProductionSummary`, `computeExecutiveInventorySummary` (reusing this codebase's own existing `inventoryCalculateCurrentStock`/`inventoryStockState` helpers rather than re-deriving stock-state logic), `computeExecutiveShippingSummary`, `computeExecutiveFinanceSummary`, `buildExecutiveDashboardKpis`, `computeExecutiveDashboardSystemHealth`. An application service, `createExecutiveDashboardApplicationService` (`apps/api/src/executive-dashboard-service.ts`), composing `orderApplicationService.listOrders()`, `productionApplicationService.listJobs()`, the inventory workspace port, `shippingApplicationService.loadShippingWorkspace()`, and `financeApplicationService.loadFinanceWorkspace()` — five already-existing read methods, no new persistence, matching §0's "read-only aggregation layer" framing exactly.

**Field-level facts checked directly before writing any code, not assumed** (§2.2's flagged risk applies here too, same as it did for PHB-5's aggregator):
- Directly confirmed frozen has **no working "efficiency" formula anywhere** — traced through `ProductionService.js`, `Production.js`, `ExecutiveDashboardAdapters.js`'s candidate-function chain (its own adapter-precedence order means the one function that could supply real data, `productionGetWorkspace`, is never even reached — `productionGetPerformanceDiagnostics` wins the candidate race first and returns read-timing diagnostics, not a business metric), and the newer `ExecutiveProductionIntelligenceService.js` (`targetAchievementPercent` exists as a ratio pattern but has no populated `targetToday` source either). Given this, `efficiency` deliberately returns `null` rather than fabricating a precise-looking but meaningless number — the honest choice given no real capacity/target concept exists in either codebase to base one on.
- `ordersToday`/`ordersThisMonth`/`newOrders`/`pendingOrders`/`delayedOrders`/`cancelledOrders` are Standalone-native definitions, not a frozen port — frozen itself never computed these fields either (§2.2's finding: none of the `*GetExecutiveSummary` functions exist anywhere in frozen, so these contract field names were never backed by real logic there). Defined here as: `newOrders` = still in Draft; `pendingOrders` = confirmed and in flight, not yet terminal; `delayedOrders` = in-flight orders past their due date. Documented as a deliberate choice, not a rediscovery.
- Finance's revenue/expense/gross-profit/net-profit/cash-balance/receivables/payables/GST-liability formulas are a direct, field-by-field verified match to this codebase's own `reports-service.ts` `statement()` function (the arithmetic backing the already-shipped, tested `GET /reports/financial` route) — read and cross-checked line by line before writing `computeExecutiveFinanceSummary`, including catching that gross profit requires subtracting `FinanceProductCost.totalCost` (cost of goods), not just being equal to revenue — an error caught and fixed during this same implementation pass, before any test ran against it. Written fresh rather than imported from `reports-service.ts`, since `statement()` is module-private and importing it would have created a circular service dependency (Reports already depends on Dashboard's workspace as one of its own inputs).
- Shipping's `pendingShipments`/`readyToDispatch` are two distinct, non-overlapping buckets (order-side ready-to-ship queue vs. shipment-side pack/ready pipeline), not a duplicate of the same number under two names — frozen never actually computed these either, so this is also a Standalone-native definition.

Full monorepo build clean. Full regression suite re-run: domain 243/243, platform 215/215, api 602/603 — the one failure is the same pre-existing, unrelated `reports-service.ts` timezone issue tracked since PHB-1.

**Not built in this increment (§4.2, Phase B, deliberately deferred):** alerts, the approvals queue, recent activity, and the intelligence panel (`salesTrend`/`topProducts`/`topCustomers`/`channelPerformance`/`manufacturingPerformance`). Per §5's own cross-cutting note, these overlap directly with PHB-7 (per-module Executive/Business Intelligence) and should be built once, consumed by both, not built twice — since PHB-7's other five modules are not yet implemented (only its Finance Intelligence piece is), building a throwaway "minimal stand-in" version now was judged not worth the cost.

## 9. Implementation record, 2026-09-16 — Phase B (alerts, approvals queue, recent activity, intelligence panel)

Authorized and implemented in this session, now that PHB-7 (all six modules) is fully built — the exact precondition §8 flagged Phase B as waiting on. **This closes out PHB-6 — both phases are now complete.** Read `ExecutiveDashboardService.js`'s `executiveDashboardBuildAlerts_`/`BuildApprovals_`/`BuildRecentActivity_`/`BuildIntelligence_` (`:213-295`) in full before writing any of this, not reconstructed from §2.4's summary. **Nothing has been committed or pushed.**

**Frozen's own alerts/approvals/recentActivity are essentially never populated in practice** — confirmed already in §8's Phase A research (frozen's `*GetExecutiveSummary` candidate functions don't exist anywhere), and re-confirmed here: frozen reads these three fields off each source module's *own* normalized payload (`source.data.criticalAlerts`/`.approvalRequests`/`.recentActivity`), which is the same payload Phase A's research already found mostly empty. This increment does not reproduce that empty-in-practice pattern. It derives genuinely real values instead, reusing already-built, already-tested PHB-7 logic wherever a direct fit exists rather than writing a second, parallel computation — the same "build once, consumed by both" principle §5 named for the intelligence panel, extended here to alerts as well since the fit turned out to be just as direct:

- **Alerts reuse Operations Risk's own per-module risk generators directly** (`computeExecutiveProductionRisks`/`InventoryRisks`/`ShippingRisks`/`FinanceRisks`, PHB-7 §8's `executive-operations-risk.ts`), fed by data Phase A already fetches for its own summary computation (`jobs`, `materials`+`movements`, `shipments`, `receivables`) — **zero new I/O**. Each risk is finalized and filtered to Medium/Critical severity (Low is not alert-worthy on a summary screen) before being mapped onto the Dashboard's two-tier alert shape (`executiveOperationsRiskToDashboardAlert`: Critical stays Critical, Medium becomes Attention). Customer risk is deliberately excluded from this reuse — it needs Customer Intelligence's full CRM+Customers+Orders pipeline, a real new dependency the Dashboard does not otherwise need, and that category stays fully visible on Operations Risk's own dedicated card regardless. Module-unavailable alerts reuse the same warning each Phase A try/catch already produces (`buildExecutiveDashboardModuleUnavailableAlert`), not a second contract-completeness ceremony.
- **Recent activity is synthesized from bulk data already available per module**, not a persisted activity log: order status changes (`Order.lastStatusChangedAt`), job completions (`ProductionJob.completedAt`), inventory movements, shipment dispatch/delivery events, and finance transactions — all real timestamps already present on data Phase A fetches (Finance's `transactions` array specifically was already being returned by `loadFinanceWorkspace()`, just not read by Phase A until now — zero new I/O there either). **Orders' own per-order activity log (`OrderActivity`) was deliberately not used**: `listActivities()` only exists per-`orderId`, with no cross-order bulk listing method — querying it for every order would be the exact same unbounded-N+1 pattern Sales Intelligence's `topProducts` was rejected for (PHB-7 §9). `Order.lastStatusChangedAt`, already on the bulk-fetched Order list, is the bounded, real-data substitute — found before assuming the gap was unresolvable, the same kind of check that resolved Production Intelligence's `dueDate`/`customerName`/`priority` "gap" into a non-issue.
- **Approvals reuse the exact bounded pattern Today's Work (PHB-5) already established and tested**: filter orders to `approvalStatus` in Pending/Changes Requested (a small subset, not all orders), then call `CustomerApprovalApplicationService.getForOrder` per matching order — bounded by construction, not a second design decision. This is the one genuinely new dependency added to the Dashboard service (`customerApproval`), small and directly precedented.
- **Intelligence panel consumes PHB-7's Sales Intelligence** (`salesTrend`/`topCustomers`/`channelPerformance`) **and Production Intelligence** (`workstationPerformance`, mapped onto frozen's `manufacturingPerformance` field name) **outputs directly**, per §5's own instruction. `topProducts` is not built here either, for the identical unbounded-N+1 reason Sales Intelligence itself left it unbuilt (PHB-7 §9) — the same gap, not a second one, kept consistent rather than silently re-attempted with a different scope.

**Two new dependencies added to `ExecutiveDashboardApplicationServiceDependencies`, both justified above and both already-existing, already-tested services**: `customerApproval` (for approvals) and `salesIntelligence`/`productionIntelligence` (for the intelligence panel). `executiveDashboardApplicationService`'s construction in `server.ts` was relocated (from before PHB-7's services existed in file order, to after) to satisfy this — a mechanical reordering, not a design change; `dashboardApplicationService`'s construction moved with it since it depends on the former. No other service's construction order was affected.
