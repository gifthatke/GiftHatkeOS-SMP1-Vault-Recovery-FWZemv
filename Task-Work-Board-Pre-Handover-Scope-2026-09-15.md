**Status:** SCOPE DOCUMENT ONLY — NOT AN IMPLEMENTATION AUTHORIZATION
**Origin:** GAP-001's expanded-scope domain sweep (Domain 11), registered as PHB-5, consolidated plan Tier 1 item 3
**Governs:** pre-handover parity blocker for the "Today's Work" task-tracking board (Canon Domain 11, Workflow/Process Automation & Orchestration — specifically the Task Governance capability)

This document is a precise implementation scope, built from a direct, complete read of the frozen source (`TaskService.js`, 269 lines; `WorkService.js`, 275 lines, both read in full), the relevant frozen UI wiring (`Script.html`, `Router.js`), the Canon Domain 11 Stage 10 certification text, and a systematic, twice-verified check of what already exists in Standalone. Standalone has not been handed over to employees; this is a pre-handover gap, not a live-incident fix.

## 0. What this scope targets, and what it deliberately does not

Canon Domain 11 certifies a large, generic enterprise Business Process Management capability: Business Processes, Workflow Definitions, Workflow Instances (with a certified `Created → Running → Waiting → Completed` lifecycle), Human Tasks, System Tasks, Automation Rules, SLA Policies, Escalation Rules, Workflow Templates, Audit Records, and AI-assisted Process Intelligence (Domain-11-Stage-10-Original.md, §10.4–§10.7). **None of that broader architecture is implemented in frozen**, confirmed in this audit's expanded-scope sweep — frozen's own `WorkflowService.js` (a nominal "UNIVERSAL WORKFLOW SERVICE") has exactly one registered entity type and one caller, so it does not constitute a real generic workflow engine either. A prior recovery-wave's own evidence card for this domain (`Domain-11-Evidence-Card.md`, 2026-09-13) reached a similar conclusion from different evidence — it cited `ApprovalService.js`/`WorkflowService.js` as the only candidate reference paths and explicitly noted "bounded approval, handoff and synchronization behavior does not prove a general orchestration platform (GAP-012)" — and, notably, **did not identify `TaskService.js` or `WorkService.js` at all**.

This scope document is about a narrower, concrete thing: within Canon's "Task Governance" capability (§10.4 — "Human tasks. System tasks. Task accountability."), frozen has a real, working, tested, UI-wired implementation of the Human Task piece — create/assign/block/complete/list tasks, aggregated into a cross-module daily work queue. That is what this document scopes for Standalone parity. It explicitly does **not** propose building Canon's fuller Workflow Definition/Instance/Automation Rule/SLA/Escalation/Process-Intelligence architecture — that remains genuinely aspirational in both codebases and is out of scope here, consistent with how every other scope document in this series has targeted "frozen's actual implemented structure," not Canon's full aspirational ceiling.

## 1. Canon grounding

Canon Domain 11, §10.4 "Certified Business Capabilities" → "Task Governance," names three things: Human tasks, System tasks, Task accountability. §10.5 "Certified Domain Boundaries" is directly relevant to `WorkService.js`'s design: the Workflow Domain "owns" Human Tasks but explicitly "collaborates with — but does not own" Customer Orders, Inventory, Production Jobs, Quality inspections, Financial transactions, Documents, and Communications. Frozen's actual implementation mirrors this boundary precisely: `WorkService.js` is a read-only aggregator that pulls status from Orders/CRM/Production/Approvals/Shipping without ever writing to them (explicitly documented in its own header comment, `WorkService.js:8-10`), while `TaskService.js` owns a genuinely separate, standalone task record with no foreign dependency on any other module's schema.

## 2. What frozen actually implements — read in full, not excerpted

### 2.1 `TaskService.js` — the task store

**Schema**: `Work_Tasks` sheet, headers `Task ID, Source Key, Entity Type, Entity ID, Module, Task Type, Title, Description, Assigned To, Assigned At, Priority, Priority Score, Due Date, Status, Workflow Stage, Blocked, Blocked Reason, Estimated Minutes, Actual Minutes, Action Module, Action Label, Customer, Created At, Created By, Updated At, Updated By, Completed At, Record Status` (`TaskService.js:7-13`).

**Write operations**: `taskCreate` (`:29-76`) — free-form `entityType`/`entityId`/`module`/`taskType`, required `title`, optional `description`/`assignedTo`/`priority`/`dueDate`/`estimatedMinutes`/`actionModule`/`actionLabel`/`customer`. Idempotent via an optional `sourceKey`: if a task with that key already exists, the existing record is returned rather than creating a duplicate (`:33-37`) — this is the hook intended for other modules to auto-generate tasks without double-creating on retry, though no other frozen module currently calls it (confirmed by repo-wide grep; only the manual UI form and test fixtures call `taskCreate`). `taskAssign`/`taskAssignToMe` (`:78-96`), `taskBlock`/`taskUnblock` (`:98-122`, blocking requires a reason, unblocking resets status to Pending), `taskComplete` (`:124-140`, refuses to complete a blocked task — "Blocked tasks must be unblocked before completion"), `taskArchive` (`:142-149`).

**Read**: `taskList`/`taskListRecords_` (`:151-169`) — filters by status/assignedTo/module, excludes Completed/Cancelled by default unless `activeOnly:false` is passed, excludes archived unless `includeArchived:true`.

**Priority scoring**: every create/update recomputes a numeric `Priority Score` (`taskPriorityScoreRecord_`, `:214-225`) by delegating to `WorkService.js`'s `workPriorityScore_` when available — the two files are coupled by design, not independent.

**IDs**: `nextEntityId_("TSK", "WORK_TASK_SEQUENCE")` (`:42`) — the same generic sequence helper (`Helpers.js:119`) used elsewhere in frozen, not the ERP84 Sequence-administration engine covered by this audit's Tax/Marketplace/Sequence pass (that engine is, per this same audit, not actually wired to anything either — consistent, not a contradiction).

**Events**: `taskPublish_` (`:254-268`) fires a `TASK_CREATED`/`TASK_ASSIGNED`/`TASK_BLOCKED`/`TASK_UNBLOCKED`/`TASK_COMPLETED`/`TASK_ARCHIVED` event via `EventDispatcher.js`'s `eventPublish_`. Not confirmed whether anything actually consumes these events (out of scope for this pass to trace further); recorded as present, not as proven-live beyond the publish call itself.

### 2.2 `WorkService.js` — the read-only cross-module aggregator

`workLoadToday()` (`:11-50`) is the single entry point. It is explicitly documented as read-only: "This release is read-only: it does not change Orders, CRM, Production, Approval or Shipping records" (`:8-10`). It:

1. Collects managed tasks from `TaskService.js` (`workCollectManagedTasks_`, `:53-64`, via `taskListRecords_({activeOnly:true})`).
2. Collects synthetic, non-persisted "tasks" from five other modules, each independently coded against that module's own field names and status vocabulary:
   - **CRM** (`:66-94`): leads needing follow-up (has a `followUp` date, or is in "Payment Pending" stage / "Requested" payment status), excluding Archived/Lost/Order-Created leads.
   - **Orders** (`:96-126`): orders not yet Delivered/Cancelled/Completed; flagged `blocked` if status is one of "Awaiting Personalization"/"Awaiting Artwork"/"Approval Pending"/"Payment Pending".
   - **Production** (`:128-156`): jobs not yet Completed/Cancelled; flagged `blocked` if stage is "Awaiting Handoff" or a `blockedReason` is set; task type becomes `QUALITY_CHECK` specifically when stage is "Quality Check".
   - **Approvals** (`:158-185`, via `approvalReadRequests_` from `ApprovalService.js`): requests not yet Approved/Rejected/Cancelled; flagged `blocked` when status is "Waiting for Customer".
   - **Shipping** (`:187-233`, via `shippingLoadWorkspace`): orders ready to ship (always `blocked:false`, due today), plus shipment exceptions (status in Delivery Failed/Customer Unavailable/RTO Initiated — always `blocked:true`, `priority:"Urgent"`).
3. Scores every task (managed and synthetic alike) with `workPriorityScore_` (`:264-274`) — base score by priority tier (Urgent 70/High 50/Medium 30/Low 10), `+35` if overdue, `+20` if due today, `+15` if blocked, `+5` if unassigned, `+25` extra specifically for `SHIPPING_EXCEPTION` tasks — and a due-state bucket (`workDueState_`, `:257-262`: overdue/today/upcoming/unscheduled).
4. Sorts by score descending, then by due date ascending; filters out completed tasks; returns the list plus summary metrics (total/urgent/overdue/blocked/dueToday/unassigned) and any per-source warnings (each collector is independently try/caught, so one module being unavailable doesn't break the whole view, `:61-63` etc.).

### 2.3 Live UI wiring — re-verified directly, not taken on an earlier pass's word

`GH.modules.TodaysWork` (`Script.html:1120-1235`) calls `workLoadToday` (`:1139`) to render the view, and binds `.tw-assign`/`.tw-unblock`/`.tw-complete`/`.tw-block` buttons plus a "New Task" form directly to `callServer("taskAssignToMe"/"taskUnblock"/"taskComplete"/"taskBlock"/"taskCreate", ...)` (`:1199-1227`). **This is not merely reachable — it is frozen's default landing screen**: `Router.js:6-13`'s `APP` config sets `DEFAULT_MODULE: "TodaysWork"`, and it is the first entry in `APP.MODULES`, ahead of `"Dashboard"`. Every employee opening frozen sees this screen before anything else, unless they navigate away. `TaskEngineTests.js` further confirms `TaskService.js` is treated as tested production code, not scaffolding.

## 4. Proposed Standalone scope

Two genuinely separate pieces, matching frozen's own file split:

**4.1 The task store (parity target for `TaskService.js`)**

- **Domain type**: `WorkTask` (fields matching §2.1's schema: `taskId, sourceKey, entityType, entityId, module, taskType, title, description, assignedTo, assignedAt, priority, priorityScore, dueDate, status, workflowStage, blocked, blockedReason, estimatedMinutes, actualMinutes, actionModule, actionLabel, customer, createdAt/By, updatedAt/By, completedAt, recordStatus`), in a new `packages/domain/src/work-task.ts` (a new file, not an addition to an existing one — this is a standalone concept with no natural existing home, unlike Attachments/Notes which belong under Order).
- **Repository port**: `createTask`, `updateTask` (covering assign/block/unblock/complete as status-transition calls, matching frozen's own decomposition rather than one generic "patch" endpoint, so the same business rules — e.g. "cannot complete a blocked task" — have one obvious place to live), `archiveTask`, `listTasks(filters)`.
- **Platform implementation**: new file, following the same `DatabaseRuntime`-parameterized factory pattern used throughout `packages/platform/src`.
- **Migration**: a new `work_tasks` table, following the existing per-domain migration-file convention.
- **Application-service methods**: mirroring `TaskService.js`'s six write operations plus list, each reusing the existing actor-derivation pattern already used throughout this codebase's other mutations (frozen's `taskActor_()` is just the active session's email — no dependency on the Assignment/user-management system; a Standalone implementation could reasonably choose to validate `assignedTo` against real user records instead, which would be a deliberate improvement over frozen's free-text field, not required for parity, and is flagged here as a design choice rather than decided).
- **Priority-score/due-state logic**: `workPriorityScore_`/`workDueState_` (§2.2, point 3) is pure business logic with no Apps-Script-specific dependency — portable close to verbatim, shared between the task store and the aggregator exactly as frozen shares it.
- **Routes**: `POST /work-tasks`, `POST /work-tasks/:taskId/assign`, `/complete`, `/block`, `/unblock`, `DELETE /work-tasks/:taskId` (archive), `GET /work-tasks`, CSRF-protected and permission-gated the same way every other mutation route already is. No `Tasks`/`Operations`/`TodaysWork` permission-module key currently exists in `permission-catalogue.ts` (checked directly) — a new one would need to be added, the same kind of decision already flagged for Attachments/Notes.

**4.2 The aggregator (parity target for `WorkService.js`)**

- **Application-service method**: `loadTodaysWork()` (or similar), composing: the new task store's `listTasks({activeOnly:true})`, plus read-only pulls from the *existing* `loadWorkspace()` methods already present on `crm-service.ts`, `order-service.ts`, `production-service.ts`, and `shipping-service.ts` (all confirmed to exist with that exact method name), plus the existing `customer-approval-service.ts` for the Approvals collector.
- **The real work here is not architectural — it's field-level translation.** Each of frozen's five synthetic-task collectors (§2.2, point 2) is coded against frozen's own exact field names and status-string vocabularies (e.g., Orders' blocked-status list `"Awaiting Personalization"/"Awaiting Artwork"/"Approval Pending"/"Payment Pending"`, Shipping's exception-status list `"Delivery Failed"/"Customer Unavailable"/"RTO Initiated"`). Standalone's equivalent domains may use different field names or status vocabularies for the same underlying states (not verified field-by-field in this pass — that level of detail is implementation work, not audit work). Faithfully porting the aggregator therefore requires re-deriving each collector's filter/blocked logic against Standalone's actual current status enums at implementation time, not a blind line-for-line copy. This is flagged as the main implementation risk in this scope, not a reason to avoid it.
- **Read exposure**: `GET /work-tasks/today` (or similar), returning the same shape frozen does: task list, summary metrics, per-source warnings (each collector independently try/caught, so one unavailable module degrades gracefully rather than breaking the whole view — worth preserving deliberately, since Standalone's own multi-service composition pattern in `dashboard-service.ts`/`reports-service.ts` does not currently do this and could benefit from the same resilience, though that's an observation, not part of this scope).

## 6. Explicitly out of scope for this document

- Canon Domain 11's fuller architecture — Business Processes, Workflow Definitions, Workflow Instances with a formal lifecycle, Automation Rules, SLA/Escalation Policies, Workflow Templates, Audit Records, AI-assisted Process Intelligence. None of this exists in frozen; building it would be new capability beyond parity, not a migration gap. See §0.
- `WorkflowService.js`'s shipment-status transition table — this is a different, narrower piece (already effectively covered by Standalone's own shipment status-transition logic, not part of the Task/Work Board).
- Automatic task-creation hooks from other modules (e.g., auto-creating a task when an order enters a blocked state) — frozen itself doesn't do this; only the manual UI form and test fixtures call `taskCreate` today, so there is no frozen behavior to reproduce here. `sourceKey`-based idempotency (§2.1) should still be carried over even though nothing currently exercises it, since it's cheap and matches frozen's schema exactly.
- Validating `assignedTo` against real Standalone user records instead of frozen's free-text email field — flagged as a reasonable improvement opportunity in §4.1, not decided.
- The `TASK_*` event-publish calls (§2.1) — carried over as schema-compatible if trivial to include, but not confirmed to have any live consumer in frozen, so not treated as a hard requirement.

## 7. Suggested sequencing, not an authorization

If authorized: (1) the task store — domain type, migration, platform implementation, repository port, application-service write/list methods, routes; (2) the aggregator — one new read-composition method pulling from the task store plus the four-to-five already-existing `loadWorkspace()`/approval-service sources, with the field-level translation work flagged in §4.2 as the primary effort; (3) UI, if in scope for whoever picks this up (out of scope for this backend-focused document). ## 9. Implementation record, 2026-09-15 — §4.2 (the aggregator)

Authorized and implemented in this session, immediately following §8. **Nothing has been committed or pushed.** Before writing any code, a dedicated research pass re-verified the exact current field names and status vocabularies of all five source services directly against their code (`crm-service.ts`, `order-service.ts`, `production-service.ts`, `shipping-service.ts`, `customer-approval-service.ts`) rather than assuming they matched frozen's — this is exactly the risk §4.2 itself flagged as the primary implementation cost, so it was treated as the first step, not an afterthought.

**Built:** `TodaysWorkItem`/`TodaysWorkMetrics`/`TodaysWorkSnapshot` types and two pure functions, `sortTodaysWorkItems` and `computeTodaysWorkMetrics` (`packages/domain/src/todays-work.ts`) — exact ports of frozen's `workLoadToday()` sort (priority score descending, then due date ascending with unscheduled tasks sorted last via the same `"9999-12-31"` sentinel) and its six-field metrics block (`total`, `urgent` at `priorityScore >= 80`, `overdue`, `blocked`, `dueToday`, `unassigned`). A new application service, `createTodaysWorkApplicationService` (`apps/api/src/todays-work-service.ts`), composing the task store (`listTasks({activeOnly:true})`) with five already-existing read methods — `crm.getLeads()`, `orders.listOrders()`, `production.listJobs()`, `shipping.loadShippingWorkspace()`, and `customerApproval.getForOrder(orderId)` — each collector independently try/caught exactly as frozen does it, so one unavailable source degrades to a warning rather than failing the whole feed (verified by test). A new route, `GET /work-tasks/today`, gated on `todayswork.workspace.read` — the permission key §8 registered as the first `SECURED_ROUTES` entry in anticipation of exactly this route, now actually wired to it.

**Field-level translation decisions, the real work here (§4.2's own framing):**
- Orders has no `orderId`/`orderNumber` field (it's `id`) and no `promiseDate`/`requiredDate`/`deliveryDate` (it's `dueDate`, falling back to `expectedDelivery`).
- Standalone's order terminal-status set is `{"Delivered","Cancelled","Refunded"}`, not frozen's `{"Delivered","Cancelled","Completed"}` — `"Completed"` isn't a Standalone order status at all, and `"Refunded"` is a Standalone-only terminal frozen doesn't have.
- Frozen's four order-blocked statuses collapse to one field (`order.status`); Standalone spreads the same concepts across four different fields. Translated as: `paymentStatus === "Pending"` → "Payment Pending"; else `approvalStatus === "Pending"` → "Approval Pending"; else `personalizationStatus === "Assets Pending"` → "Awaiting Artwork"; else `status` in `{"Ready for Personalization","Personalization","Customer Approval"}` → that status verbatim. Checked in that priority order since a single order can match more than one.
- Production has no `blockedReason` field at all (a real gap versus frozen, not a naming difference) — translated as `stage === "Awaiting Handoff"` or `qcStatus === "Rework Required"`, the two closest available signals.
- Shipping's status vocabulary is a verbatim match to frozen's (`"Delivery Failed"`, `"Customer Unavailable"`, `"RTO Initiated"` for exceptions; `"Delivered"`/`"Returned"`/`"Cancelled"` terminal) — no translation needed there, confirmed directly rather than assumed.
- Customer Approval has no cross-order listing method in Standalone at all (only `getForOrder(orderId)`) — a genuine structural gap versus frozen's `approvalReadRequests_()`, not a naming difference. **Design choice made, not previously decided in §4.2:** rather than adding a new cross-order listing port method to the Customer Approval module (out of this scope's blast radius and a separately-owned module), the Approvals collector derives its candidate order set from the Orders list already being fetched (`approvalStatus` in `{"Pending","Changes Requested"}`), then resolves detail per matching order — a deliberate, bounded N+1 over an already-small filtered set, not a new listing capability. Frozen's `"Waiting for Customer"` blocked-status has no literal Standalone equivalent; treated as `status === "Sent"` (request sent, customer hasn't responded yet), the closest available signal.

**Verification:** 31 new tests (15 application-service tests against a mock composing all five source ports, covering every collector's filter/blocked logic, the sort, the metrics, the Completed-task exclusion, and the per-source failure-isolation behavior; 5 pure-function tests for `sortTodaysWorkItems`/`computeTodaysWorkMetrics`; 4 new route source-shape tests for the `/work-tasks/today` route, its permission gate, its registration order ahead of the generic list route, and its conditional registration). Full monorepo build clean. Full regression suite re-run: domain 231/231, platform 215/215, api 594/595 — the one failure is the same pre-existing, unrelated `reports-service.ts` timezone issue tracked since PHB-1.

**PHB-5 is now fully implemented** (both §4.1 and §4.2). The Task Board employees actually see and use — create/assign/block/complete tasks, plus the cross-module "Today's Work" daily queue — has a working Standalone equivalent for the first time.
