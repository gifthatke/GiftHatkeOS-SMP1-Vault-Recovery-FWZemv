# Finance Write Workflows — Pre-Handover Implementation Scope

**Date:** 2026-09-15
**Status:** SCOPE DOCUMENT ONLY — NOT AN IMPLEMENTATION AUTHORIZATION
**Origin:** GAP-001, Domain 6, third pass (PHB-1) and second pass (PHB-2)
**Governs:** pre-handover parity blockers PHB-1 (Finance Transaction Write Workflows) and PHB-2 (Financial Planning: Budgets, Forecasts, Scenarios, Cost Centers)

This document is a precise implementation scope, built from direct reads of frozen behavior, the Canon Domain 6 text, and Standalone's existing (partially-built) Finance architecture. It is not a patch and contains no code. Writing or merging anything described here requires its own separate, explicit authorization and its own scope-lock/implementation/tests/regression/closure cycle, matching every other module in this repository. Standalone has not been handed over to employees; these are pre-handover blockers, not live-incident fixes.

## 0. The important finding this scope document is built on

Before scoping the missing pieces, this pass discovered that Standalone's Finance **domain types and repository ports are already fully built for writes**, and the **platform (database) layer already implements them**. Specifically, confirmed by direct read:

- `packages/domain/src/finance-ports.ts` already declares `saveFinanceTransaction`, `updateFinanceTransaction`, `saveFinanceExpense`, `updateFinanceExpense`, `saveFinanceIncome`, `appendFinanceCashbookEntry` on its repository port interfaces.
- `packages/platform/src/finance-repositories.ts` (354 lines) already **implements** every one of those methods against the real Postgres schema.

What is missing is narrower than "Finance has no write capability" might suggest: **the application-service orchestration layer (the business logic — validation, sequencing, permission checks, the multi-step choreography frozen's `financeRecordReceipt`/`financeRecordExpense`/`financeReverseTransaction` each perform) and the HTTP transport layer (routes) do not exist.** The foundation is built and, presumably, already covered by whatever tests exist for the platform layer; this is a scoping document for the layer that sits on top of it, not for the whole subsystem.

**Correction, 2026-09-15 (see §7): "the foundation is already built" needs qualifying, not retracting.** An independent review, subsequently verified directly against this repo, found that 7 of the Finance repository's table configurations use an `idColumn` that does not match that table's actual database primary key (e.g., `finance_product_costs` is configured with `product_cost_id`; the real column is `cost_id`). The domain types, ports, and repository *methods* are real and as described above — but `get`/`update`/upsert operations against these 7 specific tables would not work correctly against the deployed schema as currently wired. See §7 for the full list and the affected capability areas.

## 1. Canon grounding

Canon Domain 6 (Finance & Accounting), §10.6, certifies a Financial Transaction lifecycle: **Initiated → Validated → Approved → Recognized → Posted → Settled → Closed**. Canon §10.5/§10.7 name Financial Transactions, Customer Invoices, Accounts Receivable, Accounts Payable, Payments, Payment Allocations, Financial Adjustments, Budgets, and Budget Lines among the domain's permanently-owned resources. Frozen's actual transaction-status vocabulary (`Posted, Pending, Reversed` — established in Domain 6's first pass) does not match this 7-state lifecycle closely; this scope document follows frozen's actual behavior as the target for parity, per TITAN LOCK's Authority Hierarchy (frozen is the certified behavioral authority; Canon is the certified business authority, and a disagreement between them — already flagged in Domain 6's first pass — is not this document's to resolve). Where this document proposes new Standalone code, it targets frozen parity, not literal Canon-lifecycle compliance; any future desire to move Standalone's own semantics closer to Canon's named lifecycle would be a separate, explicitly-authorized decision.

## 2. PHB-1 — Finance Transaction Write Workflows

### 2.1 Record Receipt (`financeRecordReceipt`)

**Frozen behavior** (`FinanceService.js`, fully read):

1. `permissionRequire("finance.transactions.create", {resource:"finance:receipt"})`.
2. Acquire `LockService.getDocumentLock()` (the same global lock Orders itself uses — receipt recording and order saves serialize against each other in frozen).
3. Load the order; reject if not found, cancelled, or archived.
4. Reject if the order has no outstanding balance, or if the payment amount exceeds the outstanding balance (tolerance `0.001`).
5. Reject if the supplied payment reference is non-empty and already exists on another transaction (`financePaymentReferenceExists_`).
6. Generate a transaction ID (`TXN-` sequence), determine the posting date via `financeValidatePostingDate_` (a financial-period/posting-lock contract, not independently scoped in this document — see §5).
7. Append a `Finance_Transactions` row: type `"Customer Receipt"`, reference type `"Order"`, status `"Posted"`.
8. Call `financeApplyReceiptToOrder_(orderId, amount, actor, stamp)`: re-reads the order row fresh, computes new `paid`/`balance`, sets order status to `Paid`/`Partial`/`Pending` accordingly, logs an activity.
9. Post to the cashbook (`financeCashbookPost_`, `"IN"` direction).
10. Sync receivables (`financeSyncReceivables`).
11. Timeline entry, event publish (`PAYMENT_RECEIVED`), activity log.

**Known frozen ordering defect** (already recorded in this report, Domain 6 third pass): step 7 (transaction write) happens before step 8 (order update) with no shared atomicity — if step 8 fails after step 7 commits, a "Posted" transaction exists with no corresponding order-balance reduction, and (because of the payment-reference duplicate guard) a retry with the same reference is blocked rather than able to self-correct. **Do not reproduce this ordering in Standalone.** Standalone already has a working, better pattern for exactly this shape of problem — see §4.

**Proposed Standalone scope**:
- New application-service method, e.g. `recordReceipt(input)`, added to `apps/api/src/finance-service.ts`'s service (or a new `finance-transaction-service.ts` following this codebase's one-concern-per-file convention — precedent: `procurement-pr-service.ts`, `procurement-po-service.ts`, `procurement-grn-service.ts` are all separate files from the read-oriented `finance-service.ts`).
- Reuse existing: `FinanceTransactionRepositoryPort.saveFinanceTransaction`, the existing Order read/update path (`OrderMutationPersistencePort`/`order-service.ts`), `FinanceCashbookRepositoryPort.appendFinanceCashbookEntry`, `FinanceReceivableRepositoryPort` (for the receivables-sync step, if that logic is to be ported — not yet scoped in detail here).
- New: a duplicate-payment-reference check (query existing transactions by reference — confirm whether `listFinanceTransactions` supports a reference filter or whether one needs adding to the port), the outstanding-balance validation, and the order-status derivation logic (`Paid`/`Partial`/`Pending`), all as new application-layer code.
- New route: `POST /finance/receipts` (or `/finance/transactions/receipts`) in `apps/api/src/routes/finance.ts`, permission-gated on a `finance.transactions.create`-equivalent key (confirm exact key against the existing permission catalogue rather than inventing a new one — Finance's read routes already use `finance.workspace.read`/`finance.transactions.read`, suggesting a `finance.transactions.create` key may already exist in the catalogue from frozen's own key, or may need registering).
- **Atomicity**: wrap the transaction-row write and the order-balance update in one `runInTransaction`, following the pattern already proven working in `procurement-grn-service.ts`/`procurement-po-service.ts` (verify the inner order-update call is built from the same transaction scope, the same way this report's eighth/ninth passes verified for Procurement — do not assume `runInTransaction` alone is sufficient without checking the nested service is scope-bound).

### 2.2 Record Expense (`financeRecordExpense`)

**Frozen behavior** (fully read): permission check, validates total amount and category, `paymentStatus` restricted to `Paid`/`Pending`. If `Paid`: generates a transaction ID, appends a `Finance_Transactions` row (type `"Expense Payment"`, reference type `"Expense"`) **before** the expense row itself is appended. Always appends a `Finance_Expenses` row (linking the transaction ID if one was created). Posts to cashbook (`"OUT"` direction) if a transaction was created, syncs payables, timeline/event/activity as with receipts.

**Proposed Standalone scope**: same shape as §2.1 — new orchestration method (e.g. `recordExpense(input)`), reusing existing `FinanceExpenseRepositoryPort.saveFinanceExpense`, `FinanceTransactionRepositoryPort.saveFinanceTransaction` (only when `paymentStatus === "Paid"`), `FinanceCashbookRepositoryPort.appendFinanceCashbookEntry`, `FinancePayableRepositoryPort`. New route: `POST /finance/expenses`. Same atomicity requirement: the transaction write and expense write (when both occur) should be one transaction, not two independent calls — frozen's own ordering here (transaction row before expense row) has the same shape of exposure already documented for receipts and should not be copied uncritically; whoever implements this should decide the write order deliberately, inside one transaction, rather than defaulting to frozen's sequence.

### 2.3 Reverse Transaction (`financeReverseTransaction`)

**Frozen behavior** (fully read, the most complex of the three): permission check (`finance.transactions.update`), lock, load the transaction, reject if not `Posted` or if type is `Adjustment` (adjustments cannot themselves be reversed). Branches by transaction type:
- `Customer Receipt`: finds a linked Finance Income record, or falls back to reversing directly against the linked Order (`financeReverseReceiptOnOrder_`) if no Income record exists; throws if neither linkage exists.
- `Expense Payment`: requires a linked Expense record whose `paymentTransactionId` matches; throws otherwise.
- Any other type: reversal unsupported, throws.

Then: marks the original transaction `Reversed` (with the reason appended to its notes), restores the linked business state (reverses the order's paid/balance, or the linked Income, or the linked Expense's payment status, depending on target type), **appends a new `Adjustment`-type transaction** for the negative amount (an audit-preserving reversal record, not a deletion), posts an offsetting cashbook entry, re-syncs receivables or payables depending on target type, timeline/event/activity.

**Proposed Standalone scope**: this is materially more involved than §2.1/§2.2 and should probably be scoped as its own implementation slice rather than bundled with receipt/expense recording, given its branching complexity and its dependency on whichever linkage model (Income-record-based vs direct-Order-based) Standalone ends up using for receipts. Recommend implementing §2.1 and §2.2 first, then revisiting reversal with real transaction data to design against, rather than speculatively porting all of frozen's branching logic before Standalone even has transactions to reverse.

**Correction, 2026-09-15**: "wait for real transaction data" was about *design confidence*, not a hard technical dependency — an independent review correctly pointed out that correction/reversal workflows can and should be validated against deterministic test fixtures rather than waiting on live business data, which this pre-handover context won't have anyway. The suggested sequencing (§6) still places this last among PHB-1's three actions, but not because it's untestable earlier — only because it's the most complex to design correctly.

### 2.4 Two additional frozen employee actions, not in the original three-action scope

An independent review of this document, cross-checked directly against frozen source in this pass, found two more real, permission-checked, UI-wired money actions in `FinanceMoneyOperations.js` that the original three-action framing (Receipt/Expense/Reversal) omitted:

- **`financePayExpense`** (`FinanceMoneyOperations.js:149`) — a separate action for settling an *existing* unpaid (`Pending`) expense. Rejects an already-`Paid` expense, requires the settlement amount to match the expense's total (within a small tolerance), checks for a duplicate payment reference, validates the posting date via the same `financeValidatePostingDate_` chain as Receipt, creates a transaction, updates the expense's linkage/status, posts a cash outflow, and refreshes payables. Frozen's own UI confirms this is a real, separate employee workflow — a "Pay expense" button/modal, distinct from creating the expense in the first place. **This needs to be in scope alongside §2.2**: creating a `Pending` expense (§2.2's frozen behavior already covers this) without a way to later settle it would be an incomplete workflow, not full parity.
- **`financeRecordIncome`** — supports `Received`/`Pending` income; `Received` creates its own `Customer Receipt`-type transaction and cash inflow, independently of `financeApplyReceiptToOrder_` (i.e., it's not the same code path as §2.1's order-receipt flow). Confirmed to exist in frozen source; **not confirmed to have a normal employee-facing UI form** the way the other four actions do (a read tab for Income exists in frozen's Finance view, but no write form was located for it in this pass). Recommend treating this as a smaller, separately-assessed addition rather than assuming it needs the same UI investment as Receipt/Expense/Pay-Expense/Reversal — confirm actual UI reachability before scoping its Standalone form in detail.

This makes PHB-1 a four-action scope (Receipt, Expense, Pay Expense, Reversal), plus this smaller fifth item (Income) requiring its own reachability check before being sized.

## 3. PHB-2 — Financial Planning (Budgets, Forecasts, Scenarios, Cost Centers)

Frozen's `FinancePlanning.js` (v3.6.5-ERP5-FINANCE-B6) is broader than the Budget-only gap originally reported. Four sub-entities, all confirmed absent from Standalone by direct search (`forecast`/`scenario` return zero matches; `budgetId`/`financialYear` return zero matches):

### 3.1 Budgets

**Frozen behavior**: `financeSaveBudget` — a natural-key upsert. The budget's ID is deterministically derived (`financePlanningBudgetId_`: `"BUD-" + [financialYear, month, department, costCenter, category, budgetType]` joined and normalized) — saving with the same six-field combination updates the existing row rather than creating a duplicate, which is a genuinely convenient idempotent design worth preserving. On save, `financePlanningActualForBudget_` computes the actual amount by summing expenses in the given month matching the category, and remaining/variance/variance-percent are derived from it. `financeRefreshBudgetActuals(month)` recalculates actual/remaining/variance for every budget row in a given month — presumably meant to be called periodically or on demand, not automatically on every expense write (no evidence found of it being triggered from `financeRecordExpense`). `Status` defaults to `"Draft"` with **no enumerated status list and no transition validation** — an existing frozen weakness (noted in Domain 6's second pass) that a new implementation could reasonably choose to fix by adding a real status enum plus `validateStatusTransition_`-style checks (Procurement's `PROCUREMENT_STATUS_TRANSITIONS` is a proven in-repo pattern for exactly this), rather than reproducing the unchecked-string weakness — but that is a design choice for whoever scopes the actual implementation, not decided here.

**Proposed scope**: new domain types (`FinanceBudget`), new repository port and platform implementation (no existing port found — unlike PHB-1, this needs the full stack, not just the orchestration layer), new application-service methods (`saveBudget`, `refreshBudgetActuals`), new routes (`POST /finance/budgets`, `POST /finance/budgets/refresh` or similar).

**A real frozen defect found by independent review, confirmed by direct read of `FinancePlanning.js`**: `financeRefreshBudgetActuals` declares its running counter as `const updated=0` (part of one comma-joined `const` declaration) and then does `updated++` inside the per-row loop — an assignment to a constant. On any month with at least one matching budget row, this throws. This is a genuine bug in frozen, not a hypothesis — confirmed directly, not merely asserted. **Do not reproduce this in Standalone.** The fix is trivial (use `let` instead of `const` for the counter) but should be treated as a deliberate, explicit correction in the new implementation, not silently "fixed by not copying the bug and never mentioning it" — record that Standalone's version intentionally corrects this specific inherited defect.

### 3.2 Forecasts

**Frozen behavior**: `Finance_Forecasts` (`generatedAt, scenario, periodFrom/To, months, revenue, expenses, costOfGoods, grossProfit, netProfit, openingCash, forecastInflow/Outflow, projectedClosingCash, receivables, payables, gstLiability, assumptions, generatedBy`) — a generated, point-in-time financial projection record, not directly investigated beyond its header shape and seed-scenario dependency in this pass. Full behavior (the actual projection-generation function) was not read in this pass and would need its own read before scoping precisely.

### 3.3 Scenarios

**Frozen behavior**: `Finance_Scenarios`, seeded with three fixed scenarios (`Optimistic`, `Expected`, `Conservative`), each a set of multipliers (revenue, expense, COGS, collection, payment) applied to forecast generation. Fully read in this pass (`financePlanningSeedScenarios_`, `financePlanningScenario_`).

**Proposed scope**: new domain type (`FinanceScenario`), new repository port/platform implementation, likely a simple seed-and-read model (frozen itself doesn't appear to let users edit scenario multipliers through the UI, only seeds fixed ones) unless a scenario-editing capability is separately desired.

### 3.4 Cost Centers — a naming collision requiring a decision before implementation

Frozen has **two different Cost Center concepts** that a naive implementation could conflate:
- `FinancePlanning.js`'s `Finance_CostCenters` (`Cost Center ID, Cost Center Name, Department, Active, Description`), seeded with 8 fixed values (`CC-LASER, CC-PRINT, CC-PACK, CC-WAREHOUSE, CC-OFFICE, CC-CORPORATE, CC-ONLINE, CC-RETAIL`) — a simple budget-categorization tag.
- `ERP83OrganizationConstants.js`'s `Organization_Cost_Centres` (already found in Domain 8's second pass) — a richer organizational entity with branch/department linkage, an owner, a budget-owner, hierarchy, and its own permission keys.

**This document does not decide whether these should be unified into one entity, kept as two distinct ones matching frozen's own structure, or something else** — that is a real design decision requiring someone with visibility into both frozen modules' actual usage to make, not something inferable from source code alone. It is flagged here specifically so it is not accidentally decided by default (e.g., by whoever implements PHB-2 first reusing Domain 8's `Organization_Cost_Centres` without realizing a separate, simpler Finance-specific concept also exists in frozen).

## 4. Cross-cutting: use the transaction-scoped pattern this codebase already proved, not frozen's sequential-write pattern

This report's eighth and ninth passes found that Standalone's Procurement module (`procurement-grn-service.ts`, `procurement-po-service.ts`) already solves this exact class of problem correctly: wrap the whole multi-step mutation in `options.transactions.runInTransaction(async (scope) => {...})`, and construct every nested service used inside that callback from the same `scope` rather than an independent, ambient instance — confirmed, in both cases, by direct inspection of the service construction, not merely the presence of a `runInTransaction` call nearby. Whoever implements PHB-1 should follow this same pattern for `recordReceipt` (transaction write + order update in one scope) and `recordExpense` (transaction write + expense write in one scope), rather than either copying frozen's sequential-write-then-separate-update shape (already flagged as a defect in Domain 1's Orders finding, the Domain 2 BOM and lead-conversion findings, and now here) or inventing a new pattern. This is not a suggestion to deviate from frozen's *business* behavior — the validation rules, amounts, and sequencing of *what* happens should still match frozen closely — only from its *lack of atomicity*, which frozen's Apps Script foundation could not have provided even if intended.

## 6. Suggested sequencing, not an authorization

If this work is ever authorized, a defensible order based on dependency and risk:

0. **The §7.1 ID-column fix for `finance_period_locks`** — a near-zero-effort prerequisite, since the posting-guard chain every money action depends on (§7.3) won't correctly enforce day/year locks until this is corrected.
1. **PHB-1, §2.1 Record Receipt** — highest business value (this is how revenue gets recorded), and the persistence foundation is already built (modulo §7.1's fix).
2. **PHB-1, §2.2 Record Expense** — same foundation, same pattern, lower risk than reversal.
3. **PHB-1, §2.4 Pay (Settle) Expense** — a direct, small follow-on to §2.2; without it, a `Pending` expense has no way to actually be settled.
4. **PHB-2, §3.1 Budgets** — self-contained, natural-key upsert design already understood, no dependency on §2.1/§2.2. Include the §7.2 const/`updated++` correction as an explicit, recorded fix, not a silent one.
5. **PHB-1, §2.3 Reverse Transaction** — best designed with the most business context available, but testable against fixtures per §2.3's correction, not blocked on real transaction data.
6. **PHB-2, §3.2–3.4 Forecasts, Scenarios, Cost Centers** — lowest urgency; Forecasts in particular need their generation logic read and scoped properly before estimating, and Cost Centers need the naming-collision decision made first.
7. **PHB-1, §2.4 Record Income** — smallest, lowest-confidence item; confirm actual UI reachability before sizing.

This sequencing is a suggestion for whoever authorizes and scopes the actual implementation work, not a commitment made by this document.

## 8. Implementation record, 2026-09-15

PHB-1 was authorized and implemented in this session, in the order above (with Record Income resolved as described below rather than built). This section records what actually happened, as a factual record — it does not retroactively change anything decided in §1–§7.

**Built and tested, in sequence:**
1. §7.1's `finance_period_locks` column-mismatch fix.
2. Record Receipt (`POST /finance/receipts`) — full business-rule parity (order eligibility, outstanding-balance/overpayment, duplicate-reference, posting guard), wrapped in one atomic Postgres transaction spanning the transaction row, the order's payment state (via a new narrow `OrderPaymentStatePort`, deliberately not the general order-update path), the cashbook entry, and the receivable sync. 15 tests, including one confirming a mid-transaction failure leaves nothing behind, not even the transaction row.
3. Record Expense (`POST /finance/expenses`) — both `Paid` and `Pending` paths, with the conditional `accountId`/posting-guard requirement frozen itself applies only to the `Paid` case, and the asymmetry (unlike Receipt, frozen's own Record Expense has no duplicate-reference check) preserved deliberately rather than invented away. 8 new tests.
4. Pay Expense (`POST /finance/expenses/:expenseId/pay`) — settling a `Pending` expense. This surfaced a real gap in the existing Finance persistence layer: the generic repository's `update()` is a bare upsert with no existence or state check (§7.4), which would have allowed two concurrent settlement requests to both succeed. Fixed with a narrow, conditionally-guarded write (`WHERE payment_status = 'Pending'`) rather than adding a revision field across the whole Finance persistence layer. 9 new tests, including one exercising that guard directly.
5. Reverse Transaction (`POST /finance/transactions/:transactionId/reverse`) — the most complex of the five, branching by transaction type (Customer Receipt restores the order; Expense Payment restores the linked expense), appending a negative `Adjustment` record and an offsetting cashbook entry rather than deleting history, and using the same conditional-write pattern as Pay Expense to guard against a concurrent double-reversal. One frozen behavior deliberately not reproduced in full: frozen's Customer Receipt reversal prefers a linked Income record and only falls back to the Order directly. Since this implementation's Record Receipt never creates Income records (Income is the separate, distinct action addressed next), every receipt reversal here correctly takes the direct-Order path — there was no Income-linkage case to build against. 11 new tests.

**Record Income — resolved, not built.** Before implementing, two claims from this scope's own §2.4/§7.4 were independently re-verified directly against frozen source, rather than proceeding on the earlier hedge alone: (1) `financeRecordIncome`'s full function body has no `permissionRequire` call anywhere in it — confirmed by direct read, and confirmed as a real anomaly by comparing it against `financePayExpense`, defined a few lines below it in the same file, which does call `permissionRequire("finance.transactions.create", ...)` as its first line; (2) a repo-wide search found exactly one caller of `financeRecordIncome` outside its own definition — `GLP1FinanceRuntimeHotfix1Lifecycle.js`, a file explicitly named and documented as a "DISPOSABLE BUSINESS LIFECYCLE CERTIFICATION" self-test that creates temporary records and deletes them in a `finally` block. No UI form, no `Script.html` reference, no employee workflow calls it. This is not confirmed to be a real, in-use business capability — it reads as implemented-but-unused code in frozen itself. Presented to the operator as a decision (implement with a permission check added, implement exactly as frozen has it including the missing guard, or skip it) rather than resolved unilaterally, given the money-security stakes of choosing wrong. **Decision: skip.** Order Receipt and Expense recording already give employees a way to record that a customer paid and that money went out — the two concrete gaps PHB-1 was opened to close. Record Income does not fill a gap those two don't already cover, and building parity for unused, unguarded frozen code would be scope PHB-1 doesn't actually need. Not implemented; no route, service method, or platform code was added for it.

**Verification, each increment:** full monorepo typecheck clean throughout; full existing regression suite re-run after every increment (final state: platform 199/199, api 542/543 — one pre-existing, unrelated timezone failure in `reports-service.ts`, confirmed via `git stash` to fail identically on the unmodified codebase before this work began). Nothing has been committed or pushed as of this record; all of the above exists in the working tree only, pending separate explicit authorization to commit.

**PHB-1 is complete** as four of its original five identified actions, with the fifth resolved by an explicit operator decision rather than left open.

### 7.2 A real frozen defect: budget-refresh assigns to a constant

Covered in §3.1 above — recorded here for completeness of this corrections list. `financeRefreshBudgetActuals`'s `const updated=0` / `updated++` pattern throws on any matching row, confirmed by direct read of `FinancePlanning.js`.

### 7.3 The posting-guard chain, now fully traced

§5 previously listed `financeValidatePostingDate_`'s "financial-period / posting-lock contract" as not yet read. It has now been traced in full, across three files: `financeValidatePostingDate_` (`FinanceCore.js`) checks the target month has a configured, `Open` financial period, then calls `financeAssertPostingAllowed_` when defined; `financeAssertPostingAllowed_` (`FinanceProductionHardening.js`) calls `financeIsPeriodLocked_` when available and throws if the specific day, month, or year is separately `Locked`; `financeIsPeriodLocked_` (`FinanceControls.js`) checks for a matching `Locked`-status row by exact day/month/year key. **Both checks matter independently**: a financial period can be `Open` at the month level while a specific day or year lock still blocks posting. Any Standalone implementation of Receipt/Expense/Pay-Expense needs to reproduce both layers, not just the month-open check. A `financeAssertApproved_` function also exists alongside this chain but, confirmed by reading the four money-action functions directly, none of them call it — do not add an approval-workflow requirement to Receipt/Expense/Pay-Expense/Reversal on the assumption that this helper's existence implies one is enforced in frozen.

### 7.4 Full independent verification pass, 2026-09-15 — every remaining checkable claim confirmed

The rest of the external review's factual claims were subsequently checked directly, one by one, rather than left as "not independently re-verified." Every claim tested was confirmed accurate:

- **Income/Receivable/Payable ports are narrower than the headline "foundation already built" framing suggested.** Confirmed directly in `packages/domain/src/finance-ports.ts`: `FinanceIncomeRepositoryPort` exposes `listFinanceIncome`/`getFinanceIncome`/`saveFinanceIncome` — **no update method** at the interface level, which matters directly for §2.3 Reversal's Income-linkage branch. `FinanceReceivableRepositoryPort` and `FinancePayableRepositoryPort` each expose **only `list`** — no save/update at all, despite §2.1/§2.2's frozen behavior needing to sync both after every receipt/expense.
- **The generic Finance repository's `update()` is a full upsert, not an existence-checked update.** Confirmed by reading `packages/platform/src/finance.ts` and `packages/database/src/finance-persistence.ts` directly: both `save()` and `update()` call the same `saveFinanceRecord`, which does `insertInto(table).values(record).onConflict(col => col.column(idColumn).doUpdateSet(...))`. This is a real Postgres upsert — if the target row's ID doesn't already exist, `update()` silently inserts a new one instead of failing. **This sharpens §7.1's finding**: for the 7 mismatched tables, `onConflict` targets a column with no matching unique/primary-key constraint in the real schema, which Postgres will most likely reject outright with a runtime error on any write attempt (not silent data corruption) — worth confirming directly against a real database before implementation, but the likely failure mode is a hard error, which is the more benign of the two possibilities.
- **`list()` ignores its own options parameter.** Confirmed: the generic adapter's `list(_options?)` — parameter literally prefixed `_` to mark it unused — calls a plain `selectFrom(table).selectAll().execute()` with no filtering or ordering. Any archive-status filtering or the newest-first ordering frozen's own readers apply happens (if it happens at all) in a calling layer, not this adapter — relevant to any future Finance read-parity check, not just this write-scope document.
- **Finance's identity-allocator situation is now fully resolved.** `packages/platform/src/platform-runtime.ts` explicitly composes six other domains' dedicated identity allocators (customer, personalization, customer-approval, production, inventory-procurement, shipping) but no Finance one. A real, working sequence allocator does exist — `sequenceAllocateNext` in `packages/domain/src/settings-family-service.ts` — confirmed directly: it requires the `settings.manage` permission, checks the sequence is `ACTIVE`, reads the financial-year-start setting, applies the reset rule, checks for a duplicate formatted value, updates the registry under its own optimistic-concurrency version check, then does two more separate `await`s (saving the issuance record, writing an audit entry) with no visible shared transaction wrapping all three. **Conclusion, now settled rather than proposed**: Finance should not call this directly — doing so would require granting employees a Settings-management permission just to record a payment, and wouldn't give Finance's own multi-step write the shared transaction boundary it needs. Finance needs its own small, transaction-bound identity adapter, following frozen's own `TXN`/`EXP`/`FTL` prefix-and-padding format (see below), not reusing this one.
- **Frozen's own ID generation has a real, confirmed initialization gap worth knowing about, not reproducing.** `Helpers.js`'s `nextEntityId_` (the function `FinanceService.js` actually calls for `TXN`/`EXP`/`FTL`, confirmed by direct grep of all three call sites) recovers from a missing or corrupted counter by scanning for the highest existing ID — but only when the stored counter converts to a non-finite or negative number. `Number(null)` and `Number("")` both evaluate to `0`, which is finite and non-negative, so a missing or emptied counter property silently starts counting from 1 again instead of triggering recovery — a real, source-confirmed risk of reissuing an already-used ID after a property loss. Frozen's separate `NumberService.js` has a stronger, scan-based initialization helper, but confirmed it isn't what Finance actually calls — don't assume Finance inherits that stronger behavior.
- **The Forecast generation function (§5's "not yet read" item) has now been read in full** — `financeBuildStatement_` in `FinanceReporting.js`. Revenue sums Income in range with no received-status filter; Expenses sums non-Archived Expenses in range with no paid-status filter; Collections/Payments sum *Posted* Customer-Receipt/Expense-Payment transactions in range; cash balance and receivables/payables totals are **current-snapshot reads with no date-range filter at all**, not reconstructed as of the statement's end date; GST liability is period-filtered Output minus Input and can be negative. `financeGenerateForecast` takes the trailing 3 complete months of this statement, divides by 3, multiplies by a scenario's multipliers and the requested month count (clamped 1–12, no integer validation found), and projects from next month. This resolves §5's open item and should replace it as the basis for scoping §3.2 Forecasts, rather than treating the generation logic as still-unread.
- **The existing Finance closure document does not, on its own text, prove the write workflows above ever ran.** Checked directly: `docs/governance/smp1-finance-smp1-implementation-reconciliation.md` states `Status: CERTIFIED / LIVE / CLOSED / 100%` and lists API regression (492 passed), web regression, an HTTP 200 check on `/finance/workspace`, and clean build/typecheck — but nothing in its own listed evidence demonstrates a receipt, expense, settlement, or reversal actually being executed and persisted. The earlier `docs/governance/smp1-finance-s1e-scope-lock.md` does list receipts/expenses/reversals/budgets/forecasts as in-scope, but reads as an evidence-stage record, not an implementation authorization. **This does not reopen or dispute the closure** — its bytes and history are unchanged and this document doesn't propose touching it — but it means the closure should not be read as prior proof that Finance write workflows exist or were tested; it's a separate historical record with its own, narrower evidentiary basis.

The external review's proposed candidate file boundary (new `finance-money-service.ts`, `finance-money.ts`, `finance-identity.ts`, plus specific test file names) and its detailed Order-payment-port contract proposal were read and are sensible, but are implementation-time design choices consistent with — not a contradiction of — this document's own practice of flagging such decisions rather than prescribing them. Worth consulting directly when PHB-1 is actually scoped for implementation; not restated in full here.
